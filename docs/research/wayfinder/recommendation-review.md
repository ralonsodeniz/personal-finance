# Wayfinder recommendation review

**Status:** review complete; implementation follow-up remains
**Date:** 2026-08-16
**Canonical map:** [Personal Finance Platform: Stack and Initial Architecture](https://github.com/ralonsodeniz/personal-finance/issues/1)

## Purpose

The research tickets contained recommendations, and their closure was not a
substitute for reviewing every recommendation together. This ledger records
the completed review and does not make new architecture decisions. Application
and infrastructure work proceeds through separate implementation issues.

All in-scope recommendations below have now been reviewed and accepted.
Application and infrastructure implementation is tracked separately; this
review does not decide finance functionality, schemas, or API resources.

## Review decisions

- [Monorepo Orchestration and Package Layout](https://github.com/ralonsodeniz/personal-finance/issues/7) — **Accepted.** Use pnpm workspaces and Turborepo; start with `apps/web` and `apps/docs`, document `apps/mobile`, and use shared `packages/*` boundaries. Bootstrap details remain implementation follow-up.
- [TypeScript Quality Toolchain for Next.js and Expo](https://github.com/ralonsodeniz/personal-finance/issues/6) — **Accepted.** Use ESLint, Prettier, and authoritative TypeScript checks with shared flat configuration composed for Next.js and future Expo; keep Biome and Oxlint as measured alternatives.
- [Testing Strategy for Web, Backend, PWA, and React Native](https://github.com/ralonsodeniz/personal-finance/issues/3) — **Accepted.** Use Vitest, platform-specific React Testing Library, Jest plus `jest-expo` for future native tests, Playwright for web/PWA/API/auth flows, isolated PostgreSQL integration infrastructure, and Maestro as the initial native E2E candidate with a future Detox comparison.
- [Static Documentation Platform and Information Architecture](https://github.com/ralonsodeniz/personal-finance/issues/5) — **Accepted.** Use standalone Docusaurus Classic with separate developer and user-help spaces; start both trees unversioned and add versioning only when a real compatibility policy requires it.
- [PWA Installability and Online-First Runtime Strategy](https://github.com/ralonsodeniz/personal-finance/issues/2) — **Accepted with qualification.** Use Turbopack as the standard Next.js web bundler and Serwist's Next.js/Turbopack integration for the production build path and preview deployments after the compatibility spike passed. Disable service-worker registration in local development, validate PWA behavior with production builds and a deployed preview, keep authenticated data and mutations network-only, and retain Workbox `injectManifest` as the future fallback. Webpack is an emergency compatibility fallback only.
- [Cross-Platform Design System and Component Strategy](https://github.com/ralonsodeniz/personal-finance/issues/8) — **Accepted.** Share vendor-neutral design tokens and semantic foundations while keeping UI components platform-owned. Use shadcn/ui for the web/PWA now; evaluate React Native Reusables with a native styling engine in a future Expo spike. Keep Tamagui as the measured universal-component alternative and defer gluestack until its compatibility is clearer. Token generation, accessibility parity, and native implementation remain follow-up work.
- [Authentication Provider Spike: Auth0, Clerk, and WorkOS](https://github.com/ralonsodeniz/personal-finance/issues/15) — **Accepted.** Use Auth0 as the managed identity provider; keep application authorization provider-independent and park native Expo validation until mobile implementation. Tenant configuration, budget, and the implementation handoff remain follow-up work.
- [Authentication Provider and Session Strategy for Web and Mobile](https://github.com/ralonsodeniz/personal-finance/issues/9) — **Accepted.** Use server-managed encrypted web sessions and Authorization Code + PKCE with rotating refresh credentials in native secure storage; key internal identity by `(iss, sub)`. Auth0 provider configuration and the future Expo deep-link/token-rotation spike remain implementation follow-up.
- [Authorization Model for Users, Households, Roles, and Scoped Sharing](https://github.com/ralonsodeniz/personal-finance/issues/10) — **Accepted.** Keep authorization application-owned: one personal workspace per user, household workspaces with invitation-only membership and owner/editor/viewer roles, plus authenticated individual view-only grants for selective sharing. Check authorization on every protected request and within relevant transactions; apply revocation to subsequent requests; require step-up protection for high-impact actions. The API is authoritative, PostgreSQL RLS is defense in depth, and exact field visibility remains a future finance-domain decision.
- [Backend and Database Architecture for Shared Web and Mobile](https://github.com/ralonsodeniz/personal-finance/issues/14) — **Accepted.** Start with a modular monolith and managed PostgreSQL on Supabase, keeping Auth0 as the identity provider. Supabase Free is limited to local development/shared preview while no real financial data exists; use development, preview, and production environments; let Server Components call shared server-side services directly while browser client components and future Expo use the versioned API. Start bounded asynchronous work with Supabase Queues, Cron, and short Edge Function consumers; defer a paid always-on worker. Keep the SQL/domain boundary portable for a later provider or API extraction.
- [PostgreSQL ORM and Data-Access Strategy](https://github.com/ralonsodeniz/personal-finance/issues/4) — **Accepted.** Use Drizzle in a server-only `packages/db`; keep API contracts separate from database types; generate, review, commit, and CI-apply SQL migrations with one migration runner; never use production schema push or automatic synchronization. PostgreSQL remains authoritative for constraints and transactions, and integration tests use disposable PostgreSQL databases with real migrations.
- [API Contract Strategy: tRPC, REST/OpenAPI, or GraphQL](https://github.com/ralonsodeniz/personal-finance/issues/12) — **Accepted.** Use contract-first versioned REST/HTTP with OpenAPI and generated TypeScript clients for browser/PWA and Expo. Keep Server Components on the direct shared application-service path; keep ORM/server implementation types out of clients; use runtime validation, Problem Details errors, conservative financial-data caching, and contract-breaking-change checks. Retain tRPC, GraphQL, and Connect/Protobuf as conditional alternatives.
- [Deployment and CI/CD Strategy for Web, Backend, Docs, and Mobile](https://github.com/ralonsodeniz/personal-finance/issues/11) — **Accepted.** Use GitHub Actions as the control plane; Vercel for web/docs; deploy the initial Route Handler API with the web app; use development, preview, and production environments without persistent staging; apply Drizzle migrations once through protected CI; use Supabase Queues/Cron/short Edge Functions for bounded free-tier work; defer an always-on worker behind a portable OCI/queue boundary; use EAS for future mobile releases; and emit OpenTelemetry telemetry.
- [Observability, Security, Backups, and Data Export Baseline](https://github.com/ralonsodeniz/personal-finance/issues/13) — **Accepted.** Target OWASP ASVS 5.0.0 Level 2 for financial-data paths with threat-model exceptions; use OpenTelemetry as the portable telemetry boundary with strict allowlists and redaction; keep security/audit events separate from operational telemetry; require layered encrypted and isolated backups with approved RPO/RTO and restore drills; and provide authenticated, consistent, versioned JSON exports with CSV views and a manifest. Supabase Free remains suitable for development/preview but is not the final production recovery posture; Sentry is the initial operational provider per issue #18. Implementation, legal, retention, and recovery-objective details remain follow-up decisions.
- [Observability Platform for Operational Events and Errors](https://github.com/ralonsodeniz/personal-finance/issues/18) — **Accepted.** Use Sentry initially for frontend/backend errors, crashes, performance, and diagnostic context; retain OpenTelemetry as the vendor-neutral boundary; keep Grafana Cloud as a later OTel-first alternative; and keep security/audit events application-owned with redaction before egress. Region, quota, source-map, redaction, and future Expo development-build validation remain implementation follow-up.
- [Product Analytics and Usage Events Platform](https://github.com/ralonsodeniz/personal-finance/issues/19) — **Accepted.** Use PostHog in an EU Frankfurt project behind a provider-neutral adapter with explicit event/property allowlists, consent/opt-out handling, logout identity reset, fail-open behavior, usage budgets, and replay disabled initially. Keep Umami as the self-hosted/permanent-free alternative and keep product analytics separate from operational telemetry and application-owned audit events. Taxonomy, identity, DPA/consent, quota alerts, and replay/redaction validation remain follow-up.
