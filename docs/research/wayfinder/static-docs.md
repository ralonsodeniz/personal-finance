# Static documentation platform and information architecture

Date checked: 2026-08-15

## Question

Which static documentation framework and information architecture should serve developer documentation and future user-facing help? The comparison requested by issue 5 covers Docusaurus, Fumadocs, Nextra, Astro Starlight, a statically exported Next.js app, and other worthwhile options. The evaluation criteria are MDX, search, versioning, navigation, code examples, theming, accessibility, hosting, build speed, monorepo integration, and keeping developer and user documentation conceptually separate while initially sharing one docs app.

## Scope and assumptions

- This is a platform and information-architecture recommendation, not an implementation plan or a benchmark. No application code or setup files are changed by this note.
- The repository does not yet contain a docs application. The recommendation therefore assumes a standalone documentation package can be added under `apps/docs` in the existing pnpm-oriented repository. This is an inference from the current repository state, not a requirement imposed by any framework.
- “Static” means that the published site is built into HTML, CSS, JavaScript, and assets that can be served without a request-time application server. Client-side search is allowed; private, personalized, or authenticated help is out of scope for the first release.
- The first release should use one deployable docs app and one visual system, but it should not mix audiences into one undifferentiated sidebar. Developer documentation and user help have different jobs, vocabulary, release lifecycles, and success measures.
- This review uses official project documentation, official repositories, first-party hosting/framework documentation, and the W3C accessibility standard only. Qualitative ratings and the final recommendation are explicitly marked as inferences. The official sources reviewed do not provide an apples-to-apples build-time benchmark across these products.

### Docusaurus

- **Content and code examples:** Docusaurus supports Markdown and MDX, including React components embedded in Markdown, syntax-highlighted code blocks, admonitions, and interactive/live-code themes. [Markdown features](https://docusaurus.io/docs/markdown-features) · [Live codeblock theme](https://docusaurus.io/docs/api/themes)
- **Search:** the classic preset has first-class support for Algolia DocSearch. The official integration explains that the crawler indexes the public site and that contextual search can use version/type facets; local search and other providers are listed as community-maintained alternatives. [Search](https://docusaurus.io/docs/search)
- **Navigation and information architecture:** the docs model is explicitly layered as pages, sidebars, versions, and plugin instances. Sidebars can be autogenerated from the filesystem or written as ordered trees. [Docs introduction](https://docusaurus.io/docs/docs-introduction) · [Sidebar](https://docusaurus.io/docs/sidebar)
- **Versioning:** the versioning CLI copies the current docs and sidebar into versioned directories and records versions in `versions.json`. The project itself warns that versioning increases build time and codebase complexity, so it should be added when compatibility history is valuable rather than by default. [Versioning](https://docusaurus.io/docs/versioning)
- **Theming and accessibility:** the production-ready classic theme is customizable with CSS and React “swizzling”; Docusaurus presents accessibility as a design goal, not as a substitute for testing the final customized site. [Introduction](https://docusaurus.io/docs/next) · [Styling and layout](https://docusaurus.io/docs/styling-layout) · [Swizzling](https://docusaurus.io/docs/swizzling) · [Themes](https://docusaurus.io/docs/api/themes)
- **Hosting and monorepo integration:** a build emits static files in `build` that can be served by GitHub Pages, Vercel, Netlify, or another static host. The installation guide documents a `website` package beside product packages and explicitly covers pnpm and hosted monorepo base directories. [Deployment](https://docusaurus.io/docs/deployment) · [Installation and monorepos](https://docusaurus.io/docs/installation)
- **Build speed:** Docusaurus is a static generator, but the official versioning guide says versioned content increases build time. There is no official cross-framework benchmark, so “fast enough” should be verified against the expected page count and number of versioned/plugin instances. [Deployment](https://docusaurus.io/docs/deployment) · [Versioning](https://docusaurus.io/docs/versioning)
- **Assessment (inference):** this is the most complete match for the stated criteria with the least custom infrastructure. Its decisive advantage is that two conceptual doc sets can remain in one app while retaining separate paths, sidebars, and—if needed—versioning lifecycles through multiple docs plugin instances. [Multi-instance plugins](https://docusaurus.io/docs/using-plugins) · [Docs multi-instance](https://docusaurus.io/docs/docs-multi-instance)

### Fumadocs

- **Content and code examples:** Fumadocs MDX transforms Markdown/MDX into type-safe data and React Server Components. Fumadocs UI provides Shiki code blocks, tabs, steps, callouts, file-tree views, and other documentation components. [Fumadocs MDX](https://fumadocs.dev/docs/mdx) · [UI components](https://fumadocs.dev/docs/ui/components) · [Code block](https://fumadocs.dev/docs/ui/components/codeblock) · [Files component](https://fumadocs.dev/docs/ui/components/files)
- **Search:** Orama is the default search engine, with official integrations for FlexSearch, Algolia, Typesense, Orama Cloud, and custom solutions. Static builds can export indexes for browser-side search; the docs warn that large static indexes make a cloud search service more appropriate. [Search](https://fumadocs.dev/docs/search) · [Static search](https://fumadocs.dev/docs/headless/search/flexsearch) · [Custom search](https://fumadocs.dev/docs/search/custom)
- **Navigation and information architecture:** `DocsLayout` renders a sidebar from a page tree, and links/tabs can be composed into several layouts. This is a flexible base for separate developer and help roots, but the application owns the route/layout composition. [Navigation](https://fumadocs.dev/docs/navigation) · [Docs layout](https://fumadocs.dev/docs/ui/layouts/docs)
- **Versioning:** the official navigation guide describes partial versioning by folders and full versioning by maintaining a branch and deploying a separate app/subdomain. That is workable, but it is an explicit content/release strategy rather than a single built-in snapshot command. [Navigation and versioning](https://fumadocs.dev/docs/navigation)
- **Theming and accessibility:** the default UI is intentionally composable, and the CLI can copy layout components into the codebase for deeper customization. The official site emphasizes accessibility and UX; copied components stop receiving UI updates automatically, so a WCAG audit remains necessary after customization. [Fumadocs home](https://fumadocs.dev/) · [Customize UI](https://fumadocs.dev/docs/guides/customize-ui) · [WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- **Hosting and monorepo integration:** Fumadocs is normally powered by its underlying React framework, but its static-build guide documents Next.js static export and browser-side search. Its MDX workspace feature can load multiple independent content workspaces in one build, and the quick start lists Next.js, Astro with React, Waku, React Router, and TanStack Start templates. [Deploying](https://fumadocs.dev/docs/deploying) · [Static build](https://fumadocs.dev/docs/deploying/static) · [MDX workspaces](https://fumadocs.dev/docs/mdx/workspace) · [Quick start](https://fumadocs.dev/docs)
- **Build speed:** Fumadocs describes itself as fast, but the official architecture has a content layer, core layer, UI layer, and an underlying React framework. The default is server-first; static export and static search require explicit configuration. This is a reason to measure a representative build, not a reason to assume a result. [Quick start](https://fumadocs.dev/docs) · [Static build](https://fumadocs.dev/docs/deploying/static)
- **Assessment (inference):** Fumadocs is the strongest alternative if Wayfinder will need React Server Components, OpenAPI/TypeScript-driven content, custom interactive examples, or integration into an existing React application. For a standalone docs app, its flexibility trades away some of Docusaurus’s “docs product out of the box” behavior.

### Nextra

- **Content and code examples:** Nextra is a Next.js plugin for Markdown/MDX. Its docs theme includes navigation, search, sidebar, table of contents, and built-in components; the project homepage documents build-time Shiki highlighting, MDX components, tabs, steps, and file trees. [Nextra introduction](https://nextra.site/docs) · [Docs theme](https://nextra.site/docs/docs-theme/start) · [Built-in components](https://nextra.site/docs/built-ins/filetree) · [Nextra homepage](https://nextra.site/)
- **Search:** Nextra’s documented search path uses Pagefind, which indexes built HTML and serves client-side full-text search without a server. A `postbuild` step is still required, and static exports must point Pagefind at the exported output directory. [Search engine](https://nextra.site/docs/guide/search) · [Static exports](https://nextra.site/docs/guide/static-exports)
- **Navigation and information architecture:** Nextra builds a `pageMap` from the filesystem and co-located `_meta` files; `_meta` controls titles, order, nav pages, separators, menus, hidden pages, sidebars, and page-level theme options. This is enough to separate `/developers` and `/help` inside one app. [`_meta.js` file](https://nextra.site/docs/file-conventions/meta-file) · [Layout component](https://nextra.site/docs/docs-theme/built-ins/layout)
- **Versioning:** the official site exposes older Nextra documentation as separate version links, but the current docs reviewed do not document a Docusaurus-like command that snapshots a docs tree and sidebars. **Inference:** historical product docs would need separate content roots, branches/deployments, or a custom version selector and route model. [Nextra docs home](https://nextra.site/docs) · [Nextra homepage version links](https://nextra.site/)
- **Theming and accessibility:** the Docs Theme is configurable through React components and CSS, and the project calls accessibility a top priority, including respecting increased-contrast and reduced-motion preferences. These are useful defaults, not a conformance claim for custom components. [Layout component](https://nextra.site/docs/docs-theme/built-ins/layout) · [Nextra homepage](https://nextra.site/) · [WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- **Hosting and static export:** Nextra’s static-export guide uses Next.js `output: 'export'`, requires unoptimized images for that mode, and emits an `out` directory. Next.js documents that the result can be hosted by any web server that serves static assets. [Nextra static exports](https://nextra.site/docs/guide/static-exports) · [Next.js static exports](https://nextjs.org/docs/pages/guides/static-exports)
- **Build speed and monorepo fit:** Nextra can use Next.js/Turbopack in development, but its own docs note that Next.js development mode compiles each page as it is visited. The official Nextra repository uses pnpm workspaces and Turborepo, while Next.js supports transpiling local monorepo packages. **Inference:** it integrates well with a Next-oriented monorepo, but the docs-specific experience still carries Next’s application build model. [Docs theme setup](https://nextra.site/docs/docs-theme/start) · [Nextra repository](https://github.com/shuding/nextra) · [`transpilePackages`](https://nextjs.org/docs/app/api-reference/config/next-config-js/transpilePackages)
- **Assessment (inference):** Nextra is attractive for a small Next.js documentation site that values a polished default theme and Pagefind. It is less compelling than Docusaurus when independent developer/user release histories are likely, because that policy is not a documented first-class feature.

### Astro Starlight

- **Content and code examples:** Starlight supports Markdown, MDX, and Markdoc with type-safe frontmatter. Expressive Code handles syntax highlighting and advanced code annotations; built-in components cover code, tabs, steps, and asides. [Starlight home](https://starlight.astro.build/) · [Pages](https://starlight.astro.build/guides/pages/) · [Configuration reference](https://starlight.astro.build/reference/configuration/) · [Code](https://starlight.astro.build/components/code/) · [Tabs](https://starlight.astro.build/components/tabs/) · [Steps](https://starlight.astro.build/components/steps/)
- **Search:** Pagefind is the default search provider and can be configured or disabled. The configuration reference also documents merging indexes for multiple sites, which is useful if developer and help docs later split into separately deployed sites. [Configuration reference](https://starlight.astro.build/reference/configuration/)
- **Navigation and information architecture:** sidebars can be explicit or autogenerated from directories, and the theme has a page table of contents. Separate audience roots can therefore be represented as top-level directories/groups, with custom pages able to supply their own sidebar. [Sidebar navigation](https://starlight.astro.build/guides/sidebar/) · [Pages](https://starlight.astro.build/guides/pages/)
- **Versioning:** the core Starlight sources reviewed document pages, i18n, sidebars, and search but do not document a built-in historical docs snapshot/version selector. **Inference:** versioning would be implemented with version directories plus routing/build conventions, or by separate branches/deployments and a custom link structure. This should be treated as an open design decision rather than assumed capability. [Pages](https://starlight.astro.build/guides/pages/) · [Configuration reference](https://starlight.astro.build/reference/configuration/)
- **Theming and accessibility:** Starlight ships a complete theme with custom CSS and component overrides. Its official site describes it as accessible, and the override reference exposes a keyboard-focusable skip link as part of the default layout. Custom overrides still need testing against WCAG 2.2. [Starlight home](https://starlight.astro.build/) · [Overrides reference](https://starlight.astro.build/reference/overrides/) · [WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- **Hosting:** Astro’s default rendering mode is `static`, which prerenders routes at build time; the deployment guide uses the `dist` directory and lists common static and server hosts. [Astro rendering modes](https://docs.astro.build/en/basics/rendering-modes/) · [Astro deployment](https://docs.astro.build/en/guides/deploy/)
- **Build speed and monorepo fit:** Astro’s islands architecture renders static HTML by default and hydrates only explicitly interactive components, reducing browser JavaScript for content-heavy sites. Starlight can be put in a normal Astro project and supports React, Vue, Svelte, and Solid components. This is a strong qualitative performance story, but it is not a build-time benchmark, and the surrounding repository would still own an Astro app boundary. [Why Astro?](https://docs.astro.build/en/concepts/why-astro/) · [Starlight home](https://starlight.astro.build/) · [Project structure](https://starlight.astro.build/guides/project-structure/)
- **Assessment (inference):** Starlight is the best alternative if the primary goal is a fast, accessible, content-first site with minimal client JavaScript and little immediate need for release snapshots. It is a credible future choice, but Docusaurus is lower risk for the specific versioning and two-audience requirements.

### Statically exported Next.js app

- **Content and code examples:** the official `@next/mdx` integration turns `.md`/`.mdx` files into routes or imports and permits React components in MDX. The Next.js docs point to the remark/rehype ecosystem for syntax highlighting, heading links, and tables of contents; those docs features are not supplied as a single built-in docs theme. [Next.js MDX](https://nextjs.org/docs/app/guides/mdx)
- **Search and navigation:** App Router gives filesystem routes, layouts, and navigation primitives, but the official MDX guide does not provide a docs search index, docs sidebar model, or versioning workflow. **Inference:** these would be designed and maintained by Wayfinder, using Pagefind/Algolia or another search package and application-owned navigation metadata. [Next.js App Router](https://nextjs.org/docs/app) · [Next.js MDX](https://nextjs.org/docs/app/guides/mdx)
- **Versioning:** **Inference:** historical docs would require a content model and route/build logic designed by the application. Next.js static export can generate a file per route, but it does not define how versions are authored, selected, or kept compatible. [Next.js static exports](https://nextjs.org/docs/pages/guides/static-exports)
- **Theming and accessibility:** this option offers the most control because the team owns the React layout and components. Next.js provides route announcements and integrated `jsx-a11y` lint rules, but the content theme, search dialog, code tabs, and custom widgets still require an end-to-end WCAG audit. [Next.js accessibility](https://nextjs.org/docs/architecture/accessibility) · [WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- **Static hosting limits:** `output: 'export'` emits `out` and can be hosted on any static file server, but server-only features are unsupported; the official list includes API routes, rewrites, redirects, headers, proxy, ISR, and the default image loader. [Next.js static exports](https://nextjs.org/docs/pages/guides/static-exports) · [Next.js SPA/static export guide](https://nextjs.org/docs/app/guides/single-page-applications)
- **Build speed and monorepo fit:** static export produces HTML per route and benefits from route-level code splitting, but the docs-specific build pipeline is one the team must assemble. `transpilePackages` makes local workspace packages a supported integration point. **Inference:** this is a good fit when the docs must import product UI/types directly from an existing Next.js app, not when the repository only needs a standalone docs site. [Next.js static exports](https://nextjs.org/docs/pages/guides/static-exports) · [`transpilePackages`](https://nextjs.org/docs/app/api-reference/config/next-config-js/transpilePackages)

### VitePress (additional worthwhile option)

- **Content and code examples:** VitePress is an SSG for Markdown. Each Markdown file is compiled to HTML and can use Vue components; Shiki powers code highlighting, and the default theme includes the usual docs navigation and theme configuration. It is not MDX/React. [What is VitePress?](https://vitepress.dev/guide/what-is-vitepress) · [Using Vue in Markdown](https://vitepress.dev/guide/using-vue.html) · [Markdown extensions](https://vitepress.dev/guide/markdown)
- **Search:** the default theme supports local fuzzy full-text search through MiniSearch and also documents Algolia DocSearch. [Default-theme search](https://vitepress.dev/reference/default-theme-search)
- **Navigation and versioning:** the sidebar supports explicit links, groups, and autogenerated directory entries; the official docs reviewed do not describe a built-in historical docs versioning workflow. **Inference:** versioned docs would use separate roots/branches/deployments or custom routing. [Sidebar navigation](https://vitepress.dev/guide/routing) · [Default-theme navigation](https://vitepress.dev/reference/default-theme-nav)
- **Theming and accessibility:** VitePress supports extending or replacing the default Vue theme and has built-in dark-mode, language, and navigation configuration. The sources reviewed do not make a specific WCAG conformance claim, so the final site must be tested rather than inferred to be conformant. [Custom theme](https://vitepress.dev/guide/custom-theme) · [Site configuration](https://vitepress.dev/reference/site-config) · [WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- **Hosting and monorepo fit:** VitePress emits a static site to `.vitepress/dist`; its deployment guide assumes the docs site lives in a nested `docs` directory beside the rest of the project and documents pnpm/npm/yarn scripts and common static hosts. [Getting started](https://vitepress.dev/guide/getting-started.html) · [Deployment](https://vitepress.dev/guide/deploy)
- **Build speed:** VitePress uses Vite and its CLI supports static builds plus an experimental MPA mode that ships zero JavaScript by default. The official docs do not provide a comparable build benchmark. [CLI](https://vitepress.dev/reference/cli) · [Site configuration](https://vitepress.dev/reference/site-config)
- **Assessment (inference):** VitePress deserves a spike if the repository becomes Vue-oriented or if pure Markdown and local search are more important than MDX/React reuse. It is not the default recommendation for a likely TypeScript/React product because it introduces a second component model.

## Recommendation

Choose **Docusaurus classic as a standalone `apps/docs` package**, initially published as one static site. Use **two Docusaurus docs plugin instances** so the app shares the build, theme, hosting, and global search surface while keeping developer documentation and user help as separate information spaces:

```text
apps/docs/
├── docs-developer/
│   ├── getting-started/
│   ├── guides/
│   ├── reference/
│   └── contributing/
├── docs-help/
│   ├── start-here/
│   ├── tasks/
│   ├── troubleshooting/
│   └── faq/
├── sidebarsDeveloper.ts
├── sidebarsHelp.ts
└── src/pages/index.tsx
```

Use `/developers` and `/help` as the route bases, with a small landing page that clearly asks the reader to choose an audience. Docusaurus supports separate content paths, route bases, sidebars, and plugin IDs, and its multi-instance guidance explicitly covers distinct documentation sets with different versioning/release lifecycles. [Docs plugin configuration](https://docusaurus.io/docs/api/plugins/@docusaurus/plugin-content-docs) · [Multi-instance plugins](https://docusaurus.io/docs/docs-multi-instance)

The proposed policy is:

1. Keep the **developer** tree reference- and integration-oriented: SDK/API guides, architecture, configuration, examples, contributing, and compatibility notes.
2. Keep the **help** tree task-oriented: “How do I…?”, onboarding, product workflows, troubleshooting, FAQ, and user-facing explanations. Do not make users traverse developer reference categories to find a task solution.
3. Give each tree its own sidebar and navigation labels. Cross-link only where the reader is intentionally changing audience, for example “Developer API reference” or “User help for this workflow.” The separation is an information-architecture recommendation, not a claim about Docusaurus behavior.
4. Start both trees **unversioned**. Add Docusaurus versioning to developer docs when a released API/SDK actually needs historical compatibility. Add it to help only when product behavior materially diverges across supported releases; the framework warns that versioning increases build time and maintenance complexity. [Versioning](https://docusaurus.io/docs/versioning)
5. Assign stable slugs early so file renames do not silently become URL changes. [Create a doc](https://docusaurus.io/docs/create-doc)
6. Begin with one global search experience. If the result set becomes noisy, use audience/version metadata and contextual search or split the deployments later; Docusaurus’s search integration documents version/type facets and multi-instance tags. [Search](https://docusaurus.io/docs/search)

This recommendation is an **inference** from the stated requirements and the official capabilities above. Docusaurus wins because it covers the highest-risk future requirement—release-aware documentation—without requiring the team to build navigation, search wiring, and version semantics from scratch. Starlight is the performance/accessibility runner-up; Fumadocs is the integration/customization runner-up if the product becomes React-first.

## Tradeoffs

- **Docusaurus versus Starlight:** Starlight has the cleaner content-first and low-client-JavaScript story, with Pagefind and accessible defaults built into a static-first Astro theme. Docusaurus has the stronger documented versioning and multi-instance model. Choose Starlight instead if versioned docs are unlikely and a mostly static, accessible site is the dominant requirement. [Starlight](https://starlight.astro.build/) · [Astro islands](https://docs.astro.build/en/concepts/why-astro/) · [Docusaurus versioning](https://docusaurus.io/docs/versioning)
- **Docusaurus versus Fumadocs:** Fumadocs offers more composability and richer React/data-driven examples, including type-safe content and multiple search backends. Docusaurus has a more opinionated docs product and a more direct versioning path. Choose Fumadocs if direct integration with React Server Components, OpenAPI, or an existing React app is more valuable than a turnkey docs lifecycle. [Fumadocs MDX](https://fumadocs.dev/docs/mdx) · [Fumadocs navigation/versioning](https://fumadocs.dev/docs/navigation) · [Docusaurus docs introduction](https://docusaurus.io/docs/docs-introduction)
- **Docusaurus versus Nextra/Next.js:** Nextra is the faster route to a polished Next.js docs theme, while a raw Next.js app maximizes control. Both make the app boundary and static-export limitations relevant; neither is the best choice solely because the repository uses JavaScript. Choose them when the docs must share Next.js layouts, components, or local packages with the product. [Nextra docs theme](https://nextra.site/docs/docs-theme/start) · [Next.js MDX](https://nextjs.org/docs/app/guides/mdx) · [Next.js static export limits](https://nextjs.org/docs/pages/guides/static-exports)
- **Versioning cost:** versioning duplicates content/sidebar state and increases build/maintenance work. Do not introduce it on day one merely because the framework supports it. [Docusaurus versioning](https://docusaurus.io/docs/versioning)
- **Accessibility cost:** “accessible by default” or “a11y first” is a useful starting posture, not a project conformance result. The published site must be tested against WCAG 2.2, including keyboard navigation, focus visibility, skip links, search/dialog behavior, code tabs, contrast, reduced motion, headings, link purpose, and mobile layouts. [WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- **Build-time uncertainty:** no official source reviewed provides a fair benchmark across the candidates. A docs app with two plugin instances, Pagefind/Algolia indexing, MDX components, and future versions must be measured in CI rather than selected on marketing claims.
- **Static-hosting boundary:** static hosting is excellent for public docs, previews, and CDN delivery. It is not a complete answer for authenticated or personalized help; that future requirement would justify a separate runtime-backed product surface or a hybrid architecture.

## Unresolved follow-ups

1. Build a small Docusaurus spike with roughly 20 representative pages split across both trees, including MDX components, long code samples, cross-links, a 404 page, and a sample version. Record cold and cached CI build time, output size, and search-index size.
2. Run the same content fixture through Starlight and Fumadocs. Include the actual components that Wayfinder expects to embed; this is the fairest test of the Astro/React boundary and of Fumadocs’s customization cost.
3. Decide whether the product will have a supported-version policy, and if so, which surface needs versioning: developer API/SDK docs, user help, or both.
4. Confirm whether search may use a hosted index such as Algolia or must remain entirely self-hosted/client-side. Check eligibility, privacy, crawl timing, multilingual needs, and whether audience/version facets are sufficient. [Docusaurus search](https://docusaurus.io/docs/search) · [Fumadocs search](https://fumadocs.dev/docs/search) · [Nextra Pagefind](https://nextra.site/docs/guide/search) · [Starlight Pagefind](https://starlight.astro.build/reference/configuration/)
5. Decide whether docs import product types/components directly from workspace packages or only show authored examples. Direct imports favor Fumadocs/Next.js; a looser static boundary favors Docusaurus or Starlight. [Next.js `transpilePackages`](https://nextjs.org/docs/app/api-reference/config/next-config-js/transpilePackages) · [Docusaurus monorepos](https://docusaurus.io/docs/installation)
6. Define the deployment shape: separate domain or `/docs` subpath, preview environments, canonical URLs, redirects, sitemap/robots policy, and whether future user help must be hosted separately.
7. Perform an accessibility review of the chosen theme and its custom components against WCAG 2.2 before launch; include keyboard-only and screen-reader testing, not only automated linting. [WCAG 2.2](https://www.w3.org/TR/WCAG22/) · [Next.js accessibility](https://nextjs.org/docs/architecture/accessibility) · [Starlight overrides](https://starlight.astro.build/reference/overrides/)
8. Verify the supported Node.js/package-manager versions and lockfile policy at implementation time. The framework docs are live and their requirements change; this note intentionally avoids pinning a version from a research snapshot.
